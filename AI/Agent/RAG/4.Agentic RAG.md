# Agentic RAG（代理式RAG）（ReAct 循环）

如果说传统RAG是“查一次资料再回答”，Graph RAG是“沿着关系网找线索”，那么Agentic RAG就是“像研究员一样，自己决定查什么、怎么查、查得够不够，直到满意为止”。

### 🎯 核心区别：从“固定管道”到“自主循环”

它与我们之前聊的RAG范式最根本的差异，在于**控制权的转移**。

| 维度 | 传统RAG (Standard RAG) | **Agentic RAG** |
| :--- | :--- | :--- |
| **控制流程** | **固定管道**：总是“查询 → 检索 → 生成” | **动态循环**：Agent自主决定**是否**检索、**何时**检索、**如何**检索 |
| **检索方式** | **单次检索**（Single-shot），一次性从固定索引中获取结果 | **多轮迭代**（Iterative），评估结果后可能触发新的、更精细的查询 |
| **核心能力** | 擅长**简单、单跳**的事实型问题 | 胜任**多步推理、查询分解、动态工具选择**等复杂任务 |
| **语言模型角色** | 主要是**内容生成器** | **推理引擎（Reasoning Engine）**，负责规划与决策 |

一项研究中的消融实验显示，仅仅是“**从单次检索转向Agent式工具使用**”这一个改变，就能带来高达 **5.9倍** 的性能提升。

### ⚙️ 它是如何工作的？——ReAct 循环

Agentic RAG的核心是一个被称为 **ReAct（Reasoning + Acting）** 的循环模式。

1.  **推理 (Reason)**：Agent接收用户问题，分析其复杂性，并**规划**下一步行动。它会思考：“要回答这个问题，我需要先查什么？”
2.  **行动 (Act)**：基于推理，Agent**调用一个工具**（如向量检索、API查询、数据库搜索）来执行检索。
3.  **观察 (Observe)**：Agent评估返回的中间结果，判断信息是否充分、是否相关。
4.  **迭代或结束**：如果信息不足，Agent会**决定继续循环**，可能用改写后的查询再次检索，或调用另一个工具。一旦它认为收集到的上下文足够，就**跳出循环**，生成最终答案。


### 📋 它擅长解决哪类问题？

当问题超出了“一次搜索就能搞定”的范畴时，Agentic RAG的价值就凸显出来：

*   **多步推理**：需要从一个来源获取线索，再基于此去另一个来源深入查询。例如：“我们哪些产品SKU在过去90天内有关联召回？”Agent需要先查产品目录，再针对每个SKU去法规库查询。
*   **动态来源选择**：问题可能涉及多个异质数据源（API、文档库、数据库），Agent能在运行时自主判断该查哪个，而不是盲目地全查一遍。
*   **查询分解**：面对“比较东区和西区部署的可靠性SLA”这类复杂请求，Agent会将其拆解为两个独立的查询，再进行比较。
*   **迭代精炼**：首次检索结果不理想时，Agent能识别信息缺口，并用改进后的关键词或过滤器再次搜索。

### ⚠️ 代价与权衡

这种强大的灵活性并非没有成本，主要体现在：

*   **延迟更高**：多轮检索和推理循环必然导致响应时间比单次检索的传统RAG更长。
*   **Token消耗更大**：每一次循环中的推理和观察都会消耗额外的计算资源。
*   **架构更复杂**：系统不再是简单链式调用，而需要设计Agent的工具集、提示词和状态管理，实现和调试的门槛更高。

因此，Agentic RAG并非要取代传统RAG，而是为**问题复杂度超出固定管道处理能力**的场景，提供了一个更强大、但也更昂贵的解决方案。
