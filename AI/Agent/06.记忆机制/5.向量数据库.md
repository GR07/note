# 概念

在实际的 AI Agent（智能体）开发中，**知识图谱（Knowledge Graph）**和**向量数据库（Vector Database）**的结合被称为 **Graph RAG（基于图谱的检索增强生成）**。这是目前解决大模型“长期记忆”和“复杂推理”最强大的架构。

简单来说：**向量数据库负责“模糊找线索”，知识图谱负责“理清关系网”，大模型负责“总结输出”。**

# 场景设定：企业级智能客服 Agent

假设你在一家 SaaS 公司做智能客服，后台有海量的：
1. **产品手册、FAQ 文档**（非结构化文本）
2. **客户信息、订单记录、报修历史**（结构化数据）

用户问：“**我上周买的那个专业版，为什么老王说他用不了？**”

## 传统向量数据库的局限
如果只用向量数据库，它会去匹配“专业版”、“用不了”相关的文档，可能会找到一堆通用的故障排查指南。但它**不知道“老王”是谁，也不知道“我”和“老王”是什么关系**（是同事？是上下级？），更不知道“上周买的”具体是哪一笔订单。

## 知识图谱 + 向量数据库的结合流程

### 第一阶段：数据入库（构建记忆）

1. **非结构化数据（文档）**：
   * 将产品手册切分，通过 Embedding 模型变成向量，存入**向量数据库**。

2. **结构化数据（客户/订单）**：
   * 将客户表、订单表、员工表提取成三元组，存入**知识图谱**。
   * 例如：`(用户A, 购买了, 专业版)`、`(用户A, 同事是, 老王)`、`(老王, 角色是, 普通员工)`、`(专业版, 权限要求, 管理员)`。

### 第二阶段：查询检索（混合检索 Hybrid Retrieval）

当用户提问时，系统会同时进行两条线的检索：

*   **向量线（语义匹配）**：
    *   把问题变成向量，去向量数据库里找“专业版权限问题”、“无法使用”相关的**文档片段**。
*   **图谱线（实体与关系提取）**：
    *   利用大模型从问题中提取实体：`[用户A, 老王, 专业版, 上周]`。
    *   拿着这些实体去知识图谱里“顺藤摸瓜”：
        *   找到 `用户A` -> 关联到 `订单号12345` -> 状态是 `已支付`。
        *   找到 `老王` -> 角色是 `普通员工`。
        *   找到 `专业版` -> 权限要求是 `管理员`。
    *   **图谱推理得出关键事实**：“老王是普通员工，而专业版需要管理员权限，所以老王用不了。”

### 第三阶段：上下文组装（Context Assembly）

系统把两条线检索到的结果，拼装成一个超级 Prompt，发给大模型：

> **【向量检索到的文档】**：专业版软件需要管理员权限才能激活，普通员工账号无法直接使用...
> **【图谱检索到的事实】**：提问者（用户A）上周购买了专业版。用户A的同事老王是普通员工。
> **【用户问题】**：我上周买的那个专业版，为什么老王说他用不了？

### 第四阶段：生成回答

大模型结合了“文档知识”和“图谱事实”，给出精准回答：
> “您好！您上周购买的专业版软件确实已经到账。但是，根据系统记录，您提到的同事‘老王’目前是普通员工账号。专业版软件需要**管理员权限**才能激活使用。建议您先为老王升级账号权限，或者将管理员账号分享给他。”

# 技术实现架构图（简化版）

在实际代码中，这个流程通常是这样实现的：

```text
用户提问
   │
   ├──> [实体提取器 (LLM)] ──> 提取出实体 (用户A, 老王, 专业版)
   │                              │
   │                              ▼
   │                        [知识图谱查询] ──> 得到关系事实 (老王是普通员工)
   │                              │
   ├──> [Embedding 模型] ──> 向量 ──> [向量数据库查询] ──> 得到相关文档
   │                              │
   ▼                              ▼
[合并所有上下文] <─────────────────┘
   │
   ▼
[大模型 (LLM)] ──> 生成最终回答
```

# 结合时的核心技术难点与解决方案

1. **实体对齐（Entity Resolution）**：
   * *问题*：用户在对话里说“老王”，但图谱里存的是“王建国”。怎么知道是同一个人？
   * *解决*：在写入图谱时，建立别名表（Alias Table），或者用向量相似度匹配名字的 Embedding。

2. **图谱查询的“多跳”问题**：
   * *问题*：用户问“我老板的老板是谁？” 这需要图谱连续跳两次关系。
   * *解决*：使用图数据库查询语言（如 Cypher）编写多跳查询，或者让 Agent 迭代调用图谱查询工具。

3. **向量与图谱的权重融合**：
   * *问题*：如果向量检索到 10 条，图谱检索到 3 条，怎么排序给大模型？
   * *解决*：使用 **RRF（Reciprocal Rank Fusion，倒数排名融合）** 算法，根据两条线的排名重新计算综合得分，选出最相关的 Top K 条。

# 总结

**向量数据库是“广度搜索”，知识图谱是“深度推理”。**

在实际场景中，它们不是二选一，而是：
*   用**向量数据库**处理海量的、模糊的、非结构化的知识（如文档、聊天记录）。
*   用**知识图谱**处理精确的、结构化的、需要逻辑推理的关系（如人物关系、订单状态、权限规则）。
*   两者结合，才能让 AI Agent 既“博闻强识”，又“逻辑严密”。这就是目前最前沿的 **Graph RAG** 架构的核心思想。
