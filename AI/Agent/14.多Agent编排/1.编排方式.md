# 常见的编排方式

- 顺序执行（代码层面）


- 并行（代码层面）


- 交接路由（依赖模型）



- Agent既工具：
把Agent包装成一个工具，供其它的Agent使用


- 互相监督：
多个Agent之间互相监督，对Agent的最终输出结果进行评估反馈，提高解决问题的质量


- 护栏（并行Agent监督）：
一边生成一边监督，在发现输入或输出出现问题时，可以及时停下来



# 6 种多智能体（Multi-Agent）协作架构


## Single Agent（单智能体）
*   **解释**：一个 LLM 大脑，指挥几个工具（Tools）。
*   **适用场景**：任务比较简单，比如写个总结、查个天气。


## Network（网状结构）
*   **解释**：四个智能体互相连接，谁都能和谁说话，任何一个智能体都可以进行决策。
*   **适用场景**：需要多视角碰撞、复杂问题的探讨（比如多角色辩论）。


## Supervisor（监督者/主管结构）
*   **解释**：一个主管（最上面），指挥下面三个员工，由主管来决策下一步操作。
*   **适用场景**：最常用的多智能体架构。比如让一个“主管”去调度“程序员”、“测试员”和“产品经理”。


## Supervisor (as tools)（监督者作为工具）
*   **解释**：LLM 调用其他小智能体或单纯的工具，智能体作为工具，接受一个 LLM 主管的调用。
*   **适用场景**：主 LLM 负责核心规划，需要用到特定技能的“子程序”（比如专门写代码的工具、专门画图的工具）。


## Hierarchical（分级/层级结构）
*   **图解**：像一棵倒立的树，一层管一层，多级架构每级都有一个监管者。
*   **适用场景**：极其庞大、复杂的任务。比如开发一个大型软件，需要分前端、后端、测试等多个大组，每组里面还有细分。


## Custom（自定义结构）
*   **图解**：各种不规则的连线和节点，只有部分智能体具备决策权。
*   **适用场景**：根据特定任务定制的架构。可能有两个人负责决策，其他人只负责执行具体的动作，互相之间的通信也是定制化的（有些人能直接对话，有些人不能）。

---

# 总结

**Supervisor 架构**（这是目前构建多智能体最主流、最容易上手的方式，比如 LangGraph 或 AutoGen 框架）。
随着业务变复杂，再去了解 **Hierarchical** 和 **Custom** 架构。
