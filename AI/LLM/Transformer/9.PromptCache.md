


# PromptCache 的场景

在 agent 里面，每一次对话都要把全部上下文一起发送，那么最前面的对话总是在重复发送，重复的这些提示词就需要 PromptCache


# 为什么笃定 前面的提示词每次计算出来的都一样？

还是前面 KV Cache 提到的 掩码注意力机制


# 假设 修改了最前面的第 8 个 Token 呢？

那么第 8 个 Token 会重新计算生成，8 后面的所有缓存全部作废。




# 和 KV Cache 的区别

## 相同

两者缓存的都是每一层历史 Token 的 K / V 


## 不同


### 生命周期

- KV Cache 生命周期的长度只存活在这一次模型的输出

- Prompt Cache 生命周期存在于多轮对话




### 加速的环节

- KV Cache 让 decode 吐字更快

- Prompt Cach 让 Prefill 预生成更快


### 收费标准

- KV Cache 是推理引擎内部的事，用户感受不到

- Prompt Cache 是需要模型厂商规定，存在哪、存多久、命中怎么算钱





# Anthropic 官方对提示词缓存（Prompt Caching）的核心设计原则：

**按“工具 → 系统提示词 → 消息”的固定顺序拼接，确保每次请求的静态前缀完全一致**。

Anthropic 官方对提示词缓存（Prompt Caching）的核心设计原则，围绕 **“前缀复用”** 这一根本机制展开。其设计哲学可概括为：**将提示词严格划分为“稳定可缓存的前缀”与“动态变化的后缀”，并利用断点机制控制缓存边界，以极低的读取成本换取显著的延迟与费用优化。**


###  官方核心设计原则

**1. 静态前置原则（Static-First Ordering）**
提示词缓存的命中完全依赖于字节级完全一致的前缀。因此，设计时必须将**不常变化的内容放在最前面**，包括工具定义（tools）、系统指令（system）以及固定的参考文档或少样本示例；将每次请求都会变化的动态内容（如用户当前提问、最新工具返回结果）严格置于断点之后。缓存的作用域顺序是固定的：`tools → system → messages`，任何靠前部分的微小改动（哪怕是一个空格或工具参数的重命名）都会导致后续所有缓存级联失效。

**2. 断点控制原则（Explicit & Automatic Breakpoints）**
Anthropic 提供两种控制缓存边界的方式，且单次请求最多支持 **4 个缓存断点**：
*   **显式断点**：通过 `cache_control` 参数手动标记需要缓存的内容块末尾。适用于需要精细控制成本，或提示词中存在多个不同更新频率的区块（如：很少变的系统指令 + 每天变的 RAG 文档 + 每轮变的对话历史）的场景。
*   **自动缓存**：在请求顶层添加一个 `cache_control` 字段，系统会自动将断点放置在最后一个可缓存的块上，并随着对话增长自动前移。这适合不想手动管理复杂断点的通用场景。

**3. 成本不对称原则（Write Premium vs. Read Discount）**
设计提示词结构时，必须权衡缓存的“写入成本”与“读取收益”。缓存写入需要支付溢价（5 分钟 TTL 为基准价的 **1.25 倍**，1 小时 TTL 为 **2 倍**），但缓存读取仅需基准价的 **0.1 倍**（节省 90%）。这意味着：只有当同一段长前缀（官方建议通常需超过 1024 tokens）在短时间内被**重复读取多次**时，缓存设计才具有经济意义。对于一次性请求或极短提示词，缓存反而可能增加开销。

**4. 生命周期与刷新原则（TTL & Refresh on Hit）**
缓存并非永久存储。默认 TTL 为 **5 分钟**，可选扩展至 **1 小时**。关键设计原则是：**每次缓存命中都会免费重置 TTL 计时器**。因此，对于高频交互的活跃会话或智能体循环，只要请求间隔小于 TTL，缓存就能持续“保温”，无需反复支付写入费用。设计时应根据请求的疏密程度选择 TTL：高频连续对话用 5 分钟即可；存在较长停顿（如用户思考、批处理间隙）的场景则需选用 1 小时 TTL 以避免频繁重写。

**5. 数据隔离与合规原则（ZDR & Isolation）**
在架构设计上需知悉：提示词缓存符合“零数据保留”（ZDR）要求，Anthropic 不存储原始文本，仅保留内存中的 KV 缓存表示。缓存条目严格**按组织及工作区隔离**，不同工作区之间无法共享缓存。这意味着多租户应用在设计缓存策略时，无法跨租户复用同一份系统指令缓存，需在架构层面考虑这一隔离限制。

### 典型落地模式
基于上述原则，官方文档及最佳实践推荐的结构通常如下（自上而下）：
1.  **工具定义**（若稳定，置于最顶层）。
2.  **系统指令 / 长文档 / 少样本示例**（标记断点 1）。
3.  **对话历史**（标记断点 2，或由自动缓存接管）。
4.  **当前用户输入**（不标记，每次新写入）。

这种分层设计确保了最重的静态负载（如 10 万 token 的文档）只需支付一次写入溢价，后续问答仅需承担 10% 的读取成本，从而在长文档 RAG 或复杂智能体场景中实现数量级的降本与提速。



# Agent 应用

**缓存是按模型隔离的**：中途切换模型、切换推理强度，缓存命中都会失效。

**注意最小缓存长度**：目前主流模型（如 Opus 5.5、Sonnet 5.5）的最低可缓存前缀长度约为 **512 个 Token**。如果工具和系统提示词的总长度过短，可能不会触发缓存

**利用消息层传递动态信息**：如果需要在对话中更新某些状态（例如当前时间、文件变更），应通过追加新的用户消息（`role: "user"`）或工具结果来传递，而不是去编辑前面的系统提示词，这样缓存前缀就能保持完好。

**TTL（生存时间）管理**：默认缓存 TTL 为 5 分钟，每次命中都会刷新。如果业务场景请求间隔较长（如超过 5 分钟），可以考虑使用 1 小时 TTL 的缓存写入（成本为基准价的 2 倍），以避免频繁重建缓存。

**别搞滑动窗口式的裁剪**：做到只追加，不修改历史，不要觉得上下文太长浪费。

**上下文压缩不要太频繁**：压缩（上下文总结）后，所有缓存也会失效，攒一定大的长度再压缩。

可以通过监控 API 返回的 `cache_read_input_tokens` 和 `cache_creation_input_tokens` 字段，来验证缓存是否按预期命中。





### 操作显式断点具体操作步骤（以 Python SDK 为例）

作为 Agent 开发者，操作显式断点的核心是：**在构建请求时，将 `cache_control` 标记精准放置在“静态前缀的末尾”**。你需要在代码中主动构造带有该标记的内容块，而不是依赖全局开关。


**1. 标记系统提示词（System）**
如果你的 Agent 有较长且稳定的系统指令、角色设定或规则，应将其构造成内容块列表，并在最后一个文本块上添加 `cache_control`。这样，系统提示词及其之前的所有工具定义都会被纳入缓存前缀。

```python
system=[{
    "type": "text",
    "text": STATIC_SYSTEM_PROMPT,  # 你的稳定系统指令
    "cache_control": {"type": "ephemeral"}  # 显式断点
}]
```


**2. 标记工具定义（Tools）**
工具定义位于缓存层级的最前端。如果你的工具集完全稳定，可以在最后一个工具的末尾打上断点。注意：Agent 开发中**切勿在会话中途增删工具**，否则会导致整段前缀缓存失效。

```python
tools=[...你的工具列表...]
# 在最后一个工具的字典里添加：
tools[-1]["cache_control"] = {"type": "ephemeral"}
```


**3. 标记对话历史中的稳定示例（Messages）**
如果你在 `messages` 数组的开头放了少样本示例（Few-shot），可以在示例的最后一个块上标记。但**不要**将断点打在会随用户输入变化的最后一个消息块上，否则每次请求哈希都会改变，永远无法命中。



**利用多断点隔离不同频率的变更**

单次请求最多支持 **4 个**显式断点。Agent 场景下典型的分层策略是：

- **断点 1**：工具定义末尾（几乎不变）。
- **断点 2**：系统指令 + 长参考文档末尾（每次部署或会话周期内不变）。
- **断点 3**：对话历史中固定的少样本示例末尾。
- **动态消息**：当前用户输入、工具调用结果，不标记。

**监控 `cache_read_input_tokens` 验证效果**
接入后，务必在日志中打印响应体里的 `usage.cache_read_input_tokens` 字段。如果该值长期为 0，说明你的断点位置或前缀一致性出了问题，缓存根本没有被复用。
